01

Syllabus tables and seed the Python syllabus

Backend 4h Depends on: none

Before a user can be "placed" into a syllabus, a syllabus has to exist in the database. This ticket builds the two tables that hold it: one for the big levels (Beginner, Elementary, Intermediate, Advanced) and one for the topics inside each level.

Everything else this week — the diagnostic result, the results screen, the browse page — points at these rows. Build this first.

Files you'll touch

  • src/db/schema.ts
  • drizzle/ (auto-generated by the migration command)
  • src/db/seed-syllabus.ts (new)

How to build it

Add two tables. syllabus_levels: id, order, title, description. syllabus_topics: id, levelId (points at a level), order, title, blurb, conceptSlug. Seed four levels — Beginner, Elementary, Intermediate, Advanced — and spread your six existing concepts (variables-and-types, control-flow, functions, data-structures, oop, exception-handling) across them in a sensible order. Follow the same id and timestamp style already used elsewhere in the schema.

Definition of done

  • The migration runs cleanly and both tables show up with data in them.
  • Every topic points at a level that actually exists.
  • Running the seed script twice doesn't create duplicate rows.

How to check your work

npm run db:migrate && npm run db:seed:syllabus && npm run db:studio
02

Diagnostic question bank: schema and 15 seeded questions

Backend 3h Depends on: none

This is the actual 15-question test. It's written by hand and stored in the database — not generated live — so the test never breaks because an AI service is slow or down.

A test that depends on a third-party API to even load is a fragile thing to demo in front of an examiner. This one doesn't.

Files you'll touch

  • src/db/schema.ts
  • src/db/seed-diagnostic.ts (new)

How to build it

One table, diagnostic_questions: id, conceptSlug, difficulty, prompt, options (a list of 4 choices), correctOptionIndex, explanation. Write 15 multiple-choice questions spread across the six concepts — two or three questions per concept, mixing easy and harder ones. Code-writing questions can come later; keep this batch to multiple choice so it's fast to build and fast to grade.

Definition of done

  • Exactly 15 questions are seeded.
  • Every correctOptionIndex points at a real option (0 to 3).
  • Every one of the six concepts has at least one question.

How to check your work

npm run db:seed:diagnostic && npm run db:studio
03

Extend onboarding: occupation, experience, language

Backend 2h Depends on: none

Before the diagnostic test starts, the app asks a user what they do, how experienced they are, and what they want to learn. This ticket is the backend side: where those three answers get saved.

The frontend screens in ticket 6 need somewhere real to send this data. Build the landing spot first so that work isn't blocked.

Files you'll touch

  • src/db/schema.ts (users table, or a new user_profile table)
  • src/controllers/meController.ts
  • src/routes/meRoutes.ts

How to build it

Add three fields: occupation (plain text), experienceLevel (a fixed set of options — for example Student, Beginner, Some Experience, Experienced), and language (already exists as an enum — for now the only accepted value is Python). Extend the existing POST /me/onboarding endpoint to accept and save all three at once.

Definition of done

  • Sending all three fields saves them, and fetching the current user shows them back.
  • Sending an invalid experience level or a non-Python language is rejected with a clear error.

How to check your work

curl -X POST :3000/me/onboarding \ -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \ -d '{"occupation":"student","experienceLevel":"BEGINNER","language":"PYTHON"}'
04

Diagnostic endpoints: serve, grade, and place

Backend 5h Depends on: 01, 02

This is the engine room. One endpoint hands out all 15 questions. Another accepts the user's answers all at once, grades them, works out a level, writes it to the database, and tells the frontend where in the syllabus to start.

Everything the user sees on the results screen and the syllabus page comes out of this one ticket.

Files you'll touch

  • src/routes/diagnosticRoutes.ts (new)
  • src/controllers/diagnosticController.ts (new)
  • src/services/placementService.ts (new)

How to build it

GET /diagnostic/questions returns all 15 questions — never the correct answers. POST /diagnostic/submit takes the user's answers, grades them against the stored answer key, works out a score out of 15, and picks a level from that score (for example: under 40% Beginner, under 60% Elementary, under 80% Intermediate, otherwise Advanced). It saves an attempt row and calls the AI review service from ticket 5 to write the review text — if that call fails, it must still return a result using the fallback review, never an error. The response includes the score, the level, the review text, which syllabus level to start at, and a breakdown by concept.

Definition of done

  • The questions endpoint returns exactly 15 questions with no answer key visible.
  • A perfect score lands on the top level; a zero score lands on the bottom one.
  • The suggested starting syllabus level always points at a real row.
  • Submitting still works and returns a result even if the AI service is unreachable.

How to check your work

curl :3000/diagnostic/questions -H "Authorization: Bearer $TOKEN" # then answer them and post to /diagnostic/submit, try both a strong # and a weak set of answers, and try it with the AI key removed
05

AI review service, with a fallback that never fails

Backend 4h Depends on: none

This writes the two or three sentences of feedback the user reads after the test — something like "you're strong in functions, work on exception handling." It's a separate piece from ticket 4 so it can be tested on its own before it's wired in.

Free-tier AI APIs get rate-limited or slow sometimes. If this ticket only had the AI path, one bad API response could sink a live demo. The fallback text is not a nice-to-have — treat it as equally important as the AI path.

Files you'll touch

  • src/services/reviewService.ts (new)
  • .env.example

How to build it

One function, generateReview(score, breakdown, level). It calls whichever free-tier AI provider you're using, asking for a short 2-3 sentence review that names one concept the user did well on and one they should practice, based on the breakdown. Give the call a short timeout (5-8 seconds). If it errors, times out, or the key isn't set, fall back to a template built directly from the breakdown data — for example "You're strongest in {topConcept} and could use more practice with {weakConcept}." That fallback path has to work with zero network calls.

Definition of done

  • With a working API key, the review mentions a real concept from the breakdown.
  • With the key removed or invalid, a review still comes back — no crash, no empty response.

How to check your work

// call generateReview() directly with a sample breakdown, // once with a valid key and once with the key blanked out
06

Onboarding: the personal-question screens

Frontend 4h Depends on: none to start

Right after signup, before the test, the user answers a couple of quick questions about themselves: what they do, how much coding experience they have, and what they want to learn.

This is the user's first real impression of the product after login — it should feel quick and friendly, not like filling out a form.

Files you'll touch

  • src/features/onboarding/components/onboarding-page.tsx

How to build it

Add two new screens before the existing language-pick step: one for occupation (a short pick-list is friendlier than a text box — student, professional, hobbyist), one for experience level (a set of selectable cards). Keep the mascot and progress-dot style already used on the other onboarding screens. Hold all the answers in local state and send them together in one request when the user hits "Start" at the end — don't build a separate network call for each screen.

Definition of done

  • Every new screen renders and stops the user from continuing until it's answered.
  • The final submit sends occupation, experience level, and language together, in one request.

How to check your work

npm run dev # walk through onboarding in the browser, check the Network tab # for a single request carrying all three answers
07

The 15-question diagnostic player

Frontend 5h Depends on: none to start

The actual test screen. It shows one question at a time out of 15, with a visible sense of progress, and only sends everything to the server once, at the very end.

This is the screen the user spends the most time on. It should feel calm and clear — no surprises about how many questions are left.

Files you'll touch

  • src/features/diagnostic/ (new folder — components, mock data)
  • src/routes/diagnostic.tsx (new)

How to build it

Start with a small set of mock questions so this can be built before the backend endpoint (ticket 4) is ready — swap the mock for the real API call in ticket 10. Show one question at a time, a progress indicator like "6 of 15", and collect every answer in local state as the user goes. Only send everything to the server in one batch when they finish the last question, rather than a network call after each answer.

Definition of done

  • All 15 questions display in order with a visible progress indicator.
  • The final submit sends every answer in a single request.

How to check your work

npm run dev # walk through all 15 questions in the browser

09

Syllabus browse page

Frontend 4h Depends on: 01

The diagnostic result is a starting point, not a cage — the user should be able to look at every level of the syllabus, not just the one they were placed into.

People learn at different speeds. Locking someone to exactly one level would feel restrictive and isn't what was asked for.

Files you'll touch

  • src/features/syllabus/ (new folder)
  • src/routes/syllabus.tsx (new)

How to build it

List every syllabus level with its topics underneath. Mark the user's recommended starting level with a small "Recommended start" badge, but keep every other level clickable and open too. Clicking a level expands its list of topics.

Definition of done

  • All levels and their topics load and display from the database.
  • The recommended level is visually marked but nothing else is locked or disabled.

How to check your work
